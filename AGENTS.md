Nabu is a tool for harvesting JSON-LD data from a sitemap and storing it in an object store. It can either crawl individual sites or use Geoconnex bulk loader containers to stream JSON-LD to standard out. 

It is called by https://github.com/internetofwater/scheduler within a Dagster environment deployed within GCS.

The core ETL flow is: (1) `nabu harvest` reads a sitemap index (by default https://geoconnex.us/sitemap.xml) whose `<sitemap>` entries carry Geoconnex specific metadata such as `geoconnex:sitemap_id`, `geoconnex:add_associated_mainstems`, and `geoconnex:bulk_container_image`. Each sitemap is harvested into a single GeoParquet file at `summoned/<sitemap_id>.parquet` with one row per JSON-LD document and the columns `@id`, `feature_name`, `feature_description`, `geometry` (WKB), `jsonld`, `url`, `mainstem_uri`, and `s2_cell_id` (the leaf S2 cell of the geometry's centroid). The file is streamed to S3 as a multipart upload while crawling, and is only committed if the harvest succeeds and at least one document was harvested, so a failed or empty harvest leaves the previous file in place. Every harvest downloads every document and rewrites the whole file, so the file only reflects the most recent crawl; urls that fail are recorded in the crawl report and left out rather than copied from a previous harvest. A crawl report is written to `metadata/sitemaps/<sitemap_id>.json` in the metadata bucket. (2) `nabu nquads` converts the parquet files to N-Quads on stdout, putting each document in its own named graph (`urn:iow:summoned:<sitemap_id>:<base64 of @id>.jsonld`) and deterministically skolemizing blank nodes so many documents can be bulk loaded into a graph database together. (3) `nabu pull` downloads objects under a prefix and skips files whose local size and modified time match the object, since pulled files are given the object's last modified time.

The parquet files in the object store are the source of truth. Any enrichment of a document must be written into its JSON-LD in the `jsonld` column during harvest so that it is kept when the document is exported to N-Quads, which convert that column as is; an enrichment may additionally be put in its own column when it is useful to query without parsing the JSON-LD. Add enrichments as full IRIs rather than by changing the document's `@context`, and add new ones to `enrichFeature` in `internal/crawl`. For example, for sitemaps that request it, the mainstem is looked up from the document's geometry in a flatgeobuf file passed with `--mainstem-metadata` (queried with DuckDB spatial), added to the JSON-LD as a `hyf:referencedPosition`, and also stored in `mainstem_uri`. SHACL validation against the Geoconnex shape can run in process with `--shacl-local` or through a gRPC service with `--shacl-grpc-endpoint`; SHACL failures are recorded in the crawl report but are not fatal unless `--exit-on-shacl-failure` is set. Loading the N-Quads into the graph database and any downstream exports are handled by the scheduler, not by nabu.

When making changes, remember that the CLI flags and subcommands are a contract with the scheduler, which builds nabu commands as strings, so renaming or removing a flag requires a matching change there. Tests use `common.NewMockedClient` to serve sitemap and JSON-LD fixtures from `testdata/` without the network, but many integration tests also start MinIO with testcontainers and some fetch live sitemaps or remote JSON-LD contexts, so failures in a sandbox without Docker images or network access are not necessarily regressions. Follow the Go workflow of `go fmt`, `go vet`, and `go test ./...`, and keep changes consistent with the existing style of small focused functions with comments explaining why something is done rather than what it does.
